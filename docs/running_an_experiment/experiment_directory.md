# Generated Directory Layout

Running `swell create <suite>` creates an experiment directory under
`<experiment_root>/<experiment_id>`. The directory contains the resolved experiment
configuration, the generated Cylc workflow, and a copy of the Swell configuration files needed by
the workflow.

For example, if the resolved configuration contains:

```yaml
experiment_root: /discover/nobackup/my_user/SwellExperiments
experiment_id: marine-test
```

the experiment is created at:

```text
/discover/nobackup/my_user/SwellExperiments/marine-test
```

## Directory layout after `swell create`

A newly created experiment typically has the following structure:

```text
marine-test/
├── configuration/
└── marine-test-suite/
    ├── eva/                 # Present when the selected suite provides EVA templates
    ├── experiment.yaml
    ├── flow.cylc
    ├── modules
    └── modules-csh
```

The two top-level directories have different purposes:

- `configuration/` contains a copy of Swell's model, observation, and related JEDI
  configuration files.
- `<experiment_id>-suite/` is the Cylc workflow directory. This is the path passed to
  `swell launch`.

For the example above, the launch command is:

```bash
swell launch /discover/nobackup/my_user/SwellExperiments/marine-test/marine-test-suite
```

## The copied `configuration/` directory

Swell copies its configuration tree into the experiment so that tasks use the configuration
associated with that experiment rather than reading it from the Swell installation at run time.
This tree includes model interfaces, observation definitions, satellite-channel selections, and
templates used to produce application-specific YAML files.

Most users do not need to edit these files. For a one-off experiment, however, the copied files can
be useful when testing a local change to a JEDI or observation configuration. Such a change applies
only to this experiment. Re-running `swell create` with the same `experiment_root` and
`experiment_id` replaces the copied `configuration/` directory, so keep changes in the Swell source
tree when they need to be maintained and reproduced across experiments.

## The `<experiment_id>-suite/` directory

This directory contains the files Cylc needs to install and run the workflow.

### `experiment.yaml`

`experiment.yaml` is the fully resolved experiment configuration. It records the answers selected
from the suite, model, and platform defaults together with values supplied through the interactive
CLI, an override file, SLURM configuration, or command-line options. Swell tasks read this file as
the workflow runs.

Review it after creation to confirm important values such as the suite, platform, cycle range,
model components, observations, paths, and resource settings. You can edit it before launch for a
one-off test, but an [override file](understanding_configuration.md)
is the better place for changes that must be reproducible.

### `flow.cylc`

`flow.cylc` is the generated Cylc workflow definition. During creation, Swell starts with the
selected suite's workflow template and resolves its scheduling and configuration-dependent Jinja
expressions. The result defines the tasks, their dependencies, cycle points, commands, and batch
resources.

Users normally do not edit this file. Change the experiment inputs and run `swell create` again when
the generated workflow needs to change. Direct edits are best reserved for temporary workflow
development or debugging.

### `modules` and `modules-csh`

These platform-specific environment files load the required modules and set paths used by Cylc
tasks. `modules` is generated for bash shells, and `modules-csh` is its C shell
equivalent. They may include paths for Swell, JEDI, R2D2, EVA, and the platform's `spack-stack`
environment.

### `eva/`

Suites that provide EVA diagnostics include an `eva/` directory containing templates for plots and
other evaluation products. Depending on the suite and model, these can describe diagnostics for
observations, analysis increments, or JEDI log output. Workflow tasks use the templates to generate
cycle-specific EVA configuration and output under the run directory. Suites without EVA templates
do not have this directory.

## Directories created while the experiment runs

After launch (`swell launch <path_to_experment.yaml>`), tasks add working directories and output beneath the experiment root. The exact
contents depend on the selected suite, model components, and build method, but a data-assimilation
experiment commonly develops this structure:

```text
marine-test/
├── configuration/
├── marine-test-suite/
├── jedi_bundle/
└── run/
    └── <cycle-time>/
        └── <model-component>/
            ├── eva/
            ├── jedi_<application>_config.yaml
            ├── jedi_<application>_log.log
            └── ...
```

- `jedi_bundle/` contains the JEDI source and build locations used by the experiment. Depending on
  `jedi_build_method`, these may be links to an existing installation or directories populated by
  JEDI clone and build tasks.
- `run/` contains the experiment's input and output files. Swell organizes
  model-dependent work as `run/<cycle-time>/<model-component>/`.
- Each cycle/model directory can contain staged backgrounds and observations, generated JEDI YAML,
  executable logs, analysis and increment files, forecast products, and EVA output. The contents
  vary by workflow.
- A `cycle_done_<timestamp>` file indicates that the cleanup task completed for a cycle. Depending
  on the experiment's cleanup settings, some intermediate files or scratch directories may be
  removed after they are no longer needed.

Cylc job logs are not stored in this experiment tree. They are written under the user's Cylc run
directory, normally `$HOME/cylc-run/<workflow-name>/`, and include each task's `job.out` and
`job.err`. See [Monitoring an Experiment](monitoring_an_experiment.md) for details.

The experiment directory is now ready to pass to
[Launching an Experiment](launching_an_experiment.md).
